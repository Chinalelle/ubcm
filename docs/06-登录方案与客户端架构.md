# 06 · 登录方案与客户端架构

> 决策依据：`02-数智北中医架构`（接口实测）、`03-应用可达性矩阵`（30 系统移动形态）、本会话实测（CAS 登录页三种方式、JWT Bearer 鉴权）
> 本文回答两件事：**登录态怎么拿、怎么续**；**页面层怎么分三种形态落**。

**关键设计决策：Auth WebView 与 EmbedWebView 共用同一个持久化 cookie 数据仓。**
这样"登录一次"之后，内嵌的 BB / 深度辅导 / 一表通**不用再登一次**（它们都吃 CASTGC SSO）。

## 二、登录链路（含你实测到的短信验证码）

```
[冷启动]
  │
  ├─ 读本地 JWT
  │    ├─ 存在且 exp - now > 10min  → 直接进首页（0 网络）
  │    └─ 不存在/将过期              → 走静默续期
  │
  ├─【静默续期】用持久化 cookie 访问 https://i.bucm.edu.cn/tp_nup/
  │    ├─ 200 且能读到新 accessToken  → 更新 JWT，进首页（用户无感）
  │    └─ 302 到 cas/login            → 会话真过期，走【完整登录】
  │
  └─【完整登录】打开 AuthWebView
       → cas.bucm.edu.cn/cas/login?service=https://i.bucm.edu.cn/tp_nup/
       → 用户选「账号登录」：学号 + 密码
       → 触发短信验证码（你实测的"多半会发"）→ 用户填 6 位码
       → 302 回 tp_nup/cas.html?code=ST-xxx
       → 门户种 cookie: accessToken(JWT, 4h)
       → ① 从 WebView cookie 读出 accessToken
       → 写入 Keychain / Keystore
       → 关闭 AuthWebView，进首页
```

### 2.1 为什么"短信验证码"反而证明了 WebView 方案是对的

| 方案 | 遇到短信验证码时 |
|---|---|
| 纯 API 自动化登录 | **直接死**。验证码是一次性、绑会话的，脚本无法过 |
| **WebView 人工登录** | **天然可过**。用户在 WebView 里自己填，跟浏览器里一模一样 |

所以你的实测结论不是障碍，而是**"只能走 WebView"的证明**。

### 2.2 登录态的三层与持久化策略

| 层 | 载体 | 有效期 | 过期后 |
|---|---|---|---|
| L1 | `accessToken`（JWT） | **4 小时** | 用 L2 静默换新 |
| L2 | `CASTGC`（CAS 票据 cookie） | 服务端配置，通常 2–8 小时（页面无 `rememberMe`，无法延长） | 需 L3 |
| L3 | 账号密码（**不存**）+ 短信 | — | 用户手动登录 |

**结论**：一天里大概要**人工登录 1–2 次**（CASTGC 过期时）。这是服务端策略，客户端改不了。
→ 产品上必须把"重新登录"做成**低摩擦**：一键唤起、记住学号（不记密码）、验证码倒计时、失败重试。
→ **不要为了"免登录"去存密码**——这是所有方案里唯一把自己送进红线区的一步。

### 2.3 JWT 截取（工程实现）

**iOS（WKWebView）**

```swift
// 登录完成后
WKWebsiteDataStore.default().httpCookieStore.getAllCookies { cookies in
    if let t = cookies.first(where: { $0.name == "accessToken" }) {
        Keychain.save(t.value)          // 存 Keychain
    }
}
// 注意：WKWebView 的 cookie 与 URLSession 默认不共享，
// 但我们需要同步的是【Bearer 头】不是 cookie，所以原生网络层无需同步 cookie。
```

**Android（WebView）**

```kotlin
val cookie = CookieManager.getInstance().getCookie("https://i.bucm.edu.cn")
val token = cookie?.split(";")
    ?.map { it.trim() }
    ?.firstOrNull { it.startsWith("accessToken=") }
    ?.substringAfter("=")
// 存 EncryptedSharedPreferences
```

**原生请求**：`Authorization: Bearer <token>`（已实测，不认 cookie、只认这个头）。

### 2.4 JWT 校验与用户信息

JWT payload 里有：`sub`(学号)、`user_name`、`user_uid`、`mobile`、`unit_uid`、`card_type/card_id`、`avatar_*`、`exp`。
→ **不必再调接口取用户信息**，本地解 payload 即可得姓名/学号/头像/院系。
→ ⚠️ `id_number`（身份证号）也在里面，**绝不落日志、绝不进埋点、绝不渲染**。

---

### 2.5 ⚠️ 两套会话：门户吃 JWT，教务吃 JSESSIONID

这是最容易踩的坑——**登录一次 ≠ 所有系统都能用同一套凭据**：

| 系统 | 凭据形态 | 怎么来 | 原生层怎么用 |
|---|---|---|---|
| 门户 `i.bucm.edu.cn/apim/**` | **JWT**（`Authorization: Bearer`） | 登录后从 cookie 截取 | 直接带 header |
| 教务 `jw.bucm.edu.cn/jsxsd/**` | **JSESSIONID**（cookie） | WebView 访问 jw 时由 CAS SSO 自动建立 | 从 WebView cookie 仓读出 JSESSIONID，注入 OkHttp / URLSession 的 Cookie 头，再 GET HTML 解析 |
| BB / 一表通 / 图书馆 | 各自的会话 cookie | 同上，靠 CASTGC SSO | 内嵌 WebView 天然共享，无需处理 |

**含义**：
- 门户 JSON 接口 = 原生直连（轻）
- 教务数据 = HTML 抓取，但**必须先让 WebView 走一次 jw 建立会话**，再把 JSESSIONID 同步到原生网络层
- 教务的 `JSESSIONID` 与 CAS 的 `CASTGC` 是两回事：CASTGC 在 `cas.bucm.edu.cn` 域，JSESSIONID 在 `jw.bucm.edu.cn` 域

**建议做法（已实测验证）**：登录成功后，用**隐藏 WebView 访问一次**
`https://cas.bucm.edu.cn/cas/login?service=https://jw.bucm.edu.cn/`
→ 有 CASTGC 时 CAS 自动回跳到 `jw.bucm.edu.cn/jsxsd/framework/xsMain_bzy.html` 并建立 `JSESSIONID`
→ 再读 `jw.bucm.edu.cn` 域下的 JSESSIONID 存起来，教务数据全走原生 HTML 解析。

> ⚠️ 注意：直接访问 `jw.bucm.edu.cn/jsxsd/xxx` 会落到**强智自己的登录页**（不自动跳 CAS），所以必须从 CAS 的 `service=` 入口进。这一步不做，会误判"教务不吃 SSO"。

## 三、页面层：三种形态

你定的两层（原生页面 + 内嵌网页）是对的，我再补一层"跳出"，因为有些系统在 WebView 里物理上打不开。

| 形态 | 技术 | 适用 | 数量 |
|---|---|---|---|
| **A. 原生页面** | Compose / SwiftUI，数据走 ApiClient | 课表、通知、成绩、考试、空教室、待办、日程 | 主体 |
| **B. 内嵌 WebView** | 共用持久化 cookie 仓 | BB、深度辅导、智慧后勤、图书馆、一表通、云盘 | 6–8 个 |
| **C. 跳出企业微信** | URL Scheme / Universal Link | 一卡通、缴费、教务移动端、采购 | 4–5 个 |

### 3.1 A 形态（原生）的边界

**能做**：门户 `/apim` 的 JSON 接口（应用清单、待办、消息、日程、天气、问答）+ 教务的 HTML 表格（课表/成绩/考试/空教室，规则已有）。
**不能做**：任何写操作（选课、报名、评价）、需要微信环境的、一卡通。

### 3.2 B 形态（内嵌）的准入清单

来自 `03-应用可达性矩阵` 的体检结果，只有这几类**值得且能够**内嵌：

| 系统 | 地址 | 为什么可以 | 要注意 |
|---|---|---|---|
| **深度辅导** | `sdfd.bucm.edu.cn` | 全校唯一 Nuxt 真响应式，`viewport-fit=cover` 支持 iOS 安全区 | 几乎零改造 |
| **智慧后勤** | `zhhq.bucm.edu.cn/wx/#/basicHome` | 独立 m 站（hash 路由 H5），`user-scalable=no` | 依赖微信 JS-SDK 的定位/扫码，需测 |
| **BB** | `bb.bucm.edu.cn` | 走 CAS SSO，WebView 有 CASTGC 可免登 | **任意路径都 200 登录页**，必须 JS 注入判登录成功 |
| **一表通** | `workflow.bucm.edu.cn` | 有 40 个 `m_matterApplication` 移动路由 | 133 个流程只做导航，不重做 |
| **图书馆** | `slib.bucm.edu.cn` | 超星 SPA | 需逆向 XHR 才知接口；先内嵌整站 |
| **云盘** | `cloudpan.bucm.edu.cn` | — | 登录靠 CAS |

### 3.3 C 形态（必须跳出）—— 不是你懒，是物理限制

| 系统 | 为什么不内嵌 | 做法 |
|---|---|---|
| 教务移动端 `jw/njwhd/login/wechatcp` | 服务端 **302 到微信 OAuth**，非微信环境进不去 | 跳企业微信，或直接用桌面版 `jw.bucm.edu.cn/jsxsd`（需 ATS 例外） |
| 缴费 `jiaofei.bucm.edu.cn` | 仅企业微信 OAuth（`snsapi_userinfo`） | 跳企业微信 |
| 采购 `cgpt` | 同上（`agentid=1000122`） | 跳企业微信 |
| 一卡通 e卡通 | 无网页入口，只有企微小程序 | 跳企业微信 |
| 轻新课堂 `qxkt:88` | **HTTP 明文 + 端口 88 + 无 TLS** | 只能跳浏览器（且 iOS 需用户确认） |

## 四、五个必须提前解决的工程难题

### ① 内嵌页怎么判"登录成功"（最坑的一个）

BB 和很多系统**任意路径都返回 200**，`onPageFinished` 收到 200 不等于登录成功。
**解法：注入 DOM 探针，而不是看 HTTP 状态码。**

```javascript
// 判定规则示例（BB）
!!document.querySelector('#ac-login, .login-page')   // 有登录表单 = 没登录
|| location.href.includes('/webapps/login')
```
统一封装成 `LoginDetector(host) → rules[]`，每个内嵌域配一组规则，命中则切回原生登录流程。

### ② iOS ATS 明文主机

必须进 `Info.plist` 的 `NSAppTransportSecurity` 例外（或强制走 HTTPS）：

| 主机 | 问题 | 处理 |
|---|---|---|
| `qxkt.bucm.edu.cn:88` | HTTP + 88 端口，该端口无 TLS | 不内嵌，只跳转 |
| `jy.bucm.edu.cn` | CAS service 参数写成 http | 用 `https://` 访问 |
| `lab/sjjx` | `202.204.38.93` 纯 IP | 换 `https://sjjx.bucm.edu.cn/sso/`（实测可用） |

### ③ WebView 安全（JWT 会路过这里）

- Auth WebView **只允许白名单域名**（cas / i.bucm / jw / bb …），禁止任意跳转
- 禁止 `addJavascriptInterface`（Android）暴露原生能力给网页
- 禁止在 WebView 里加载第三方广告/统计脚本
- 关闭 `file://` 访问、`allowUniversalAccessFromFileURLs`
- **JWT 读到后立即从 WebView 内存中"遗忘"**：不清 cookie（要续期），但不在任何日志/崩溃上报里出现

### ④ 登录态过期时的全局处理

ApiClient 收到 `{"code":0,"msg":"未传递 access_token..."}` 或 401 → 统一拦截 → 触发静默续期 → 失败再弹登录。
**禁止每个页面各自处理**，否则会出现"五个页面同时弹登录框"。

### ⑤ 明文 HTTP 的 WebView 降级

Android 9+ 默认禁明文，需要 `networkSecurityConfig` 白名单；iOS 需要 ATS 例外。
但要清楚：**给明文域名开例外，是审核员会问的点**，能在清单里写清"仅内网/仅旧系统"更好。

## 五、技术选型（复用现有资产）

| 层 | 选型 | 理由 |
|---|---|---|
| Android | Kotlin + Compose（AGP 9 内置 Kotlin） | 与 KechTable/NotePlus 同一套工具链，课表渲染与胶囊经验可直接搬 |

## 六、和合规的关系（一句话）

这套架构的性质是：**用户本人在自己的设备上、用自己的账号登录、数据只存在本机**——落在 05 文档的🟡黄档，不是红线。
红线是被这三件事踩出来的：①存用户密码 ②把 JWT 集中到服务器 ③把登录能力提供给他人。**架构上天然避开即可。**
