# 16 · 原生登录（不跳网页）

> 交付时间：2026-11-21 夜　承接 `15-登录门禁.md`
> 本轮做完的：**登录页改成学号+密码表单，直接和 CAS 通信换齐凭证，全程不打开网页**
> 一句话结论：**DES 加密与 OAuth2 码流都逆向清楚了，四条凭证可以纯 native 换到；只有图书馆座位 `ic-cookie` 仍需网页补一次。**

---

## 一、需求与边界

**用户诉求**（2026-11-21）：
> 登陆打开网页后会每个网页跳转一遍，实际只登陆数字北中医即可。做成一个简洁的页面，输入用户名与密码，如果要求验证码就额外出现验证码框。输入完成后用这条数据直接获取所有凭证，不跳转到任何网页。

**这条需求碰到了红线，必须先划清边界**：

| 红线 | 本实现怎么守 |
|---|---|
| 🔴 不代登录 | 用户**本人在自己设备**上输入自己的学号密码；App 不为他人登录、不托管 |
| 🔴 不存密码 | 密码只在 `LoginViewModel.login()` 的入参里活一次；`UiState` 里**没有** password 字段（编译期就不可能被存）；不写 prefs、不写日志 |
| 🔴 不托管凭证 | 仍然只存本机 SharedPreferences，不出设备 |
| 🔴 不破解验证码 | 需要验证码时显示图片给用户自己填，不做识别 |

**已知局限（诚实说明）**：Kotlin 的 `String` 不可变，**内存里的明文无法主动擦除**，
只能保证「不落盘、不外发、活不过这次调用」。

## 二、CAS 登录：密码不是明文提交的

### 2.1 前端做了什么

登录页（`cas.bucm.edu.cn/cas/login`）的账号表单里，`un`/`pd` 只是给人看的输入框，
真正提交的是三个隐藏字段（`login10.js:153-155`）：

```js
$("#ul").val(u.length);                              // 用户名「长度」
$("#pl").val(p.length);                              // 密码「长度」
$("#rsa").val(strEnc(u + p + lt, '1', '2', '3'));    // 加密串
```

⚠️ **`ul`/`pl` 是长度而不是值** —— 最容易搞错的一处。

### 2.2 `des.js` 不是标准 DES（本轮最大的坑）

`strEnc` 的实现是"按 4 个 UTF-16 字符一块、三次独立 DES（E-E-E）、输出大写 hex"。
看起来就是标准 DES，于是我先用 `javax.crypto` 的 `DES/ECB/NoPadding` 实现，**结果对不上**。

逐步定位：

| 检查项 | 结论 |
|---|---|
| 经典向量 key=`133457799BBCDFF1` / pt=`0123456789ABCDEF` | 标准 DES = `85E813540F0AB405`（openssl 验证）；`des.js` = **`CC38B78305003643`** |
| `initPermute` / `finallyPermute` / `expandPermute` 表 | 逐项核对，都是标准的 |
| PC-1 / PC-2 / P 置换 / 8 个 S 盒 | 逐项核对，都是标准的 |
| `des.js` 自身 enc/dec 闭环 | 正常（能解回原文） |

**结论：它是个"自洽的非标准 DES 变体"**——表全标准、结果非标准。
学校后端用的就是同一套变体，所以**只能逐行移植，不能"优化"成 javax.crypto**。

移植结果（`DesLegacy.kt`，240 行位数组 + 魔数表）用**原版 `des.js` 在 node 里的输出逐字节对拍**：

```bash
strEnc("abcd","1","2","3")  → A9CF2704230383D1      ✅ 一致
strEnc("abc","1","2","3")   → 39644174795FB4D0      ✅ 一致
真实 66 字符登录串          → 272 hex 逐字节一致     ✅ 一致
```

`CasCryptoTest` 里还专门有一条**反向断言**：`assertNotEquals(标准DES结果, 我们的结果)` ——
哪天有人"顺手优化"成 javax.crypto，测试立刻红。

### 2.3 决定性验证：加密格式被服务端接受

用假账号（`99999999999`）+ 假密码 POST 一次，服务端返回：

```
连续登录失败15次，账号将被锁定10分钟，剩余次数15
```

**进的是「密码错误」分支而不是「参数错误」** → 说明加密格式正确、字段名正确、长度字段正确。
（这一步不需要真实密码就能做，是整轮最有价值的验证。）

### 2.4 风控：失败 15 次锁 10 分钟

上面那句就是风控提示。所以实现里定死两条：

1. **绝不自动重试** —— 一次失败就把原因摆给用户
2. 失败后 `execution` 会从 `e1s1` 推进到 `e1s2`，**同一份 lt/execution 不能重复提交**，
   每次都要重新 GET 登录页

## 三、拿到 CASTGC 之后：四条凭证怎么换

| 凭证 | 路径 | 状态 |
|---|---|---|
| 门户 `accessToken` | CAS → 门户落地 → **OAuth2 码流** → `casToken` | ✅ 实测 |
| 教务 `JSESSIONID` 整串 | CAS → `jw.bucm.edu.cn/` | ✅ 实测 |
| 一卡通 `servicehall` + `openid` | `EcardApi.login(castgc)`（既有） | ✅ 实测 |
| 座位 `ic-cookie` | CAS → `authcenter/doAuth` → `auth/token` | ❌ **仍需网页**（见 §3.2） |

### 3.1 门户 accessToken 不能用 cookie —— 它根本不下发

最初我以为跟完 CAS 重定向就能从 `Set-Cookie` 里捡到 `accessToken`。**实测没有。**

读门户前端才发现：`accessToken` 是 **`cas.html` 用 JS 自己写进 cookie 的**：

```js
$.get(contextpathAuthc + "/oauth2/casToken/" + code + "/" + oauth_client_id + "?casDelegate=", function (obj) {
    if (obj.code == 200) $.cookie("accessToken", obj.data.accessToken)
})
```

所以纯 native 必须自己走完 OAuth2：

```
1) GET  cas?service=https://i.bucm.edu.cn/tp_nup/     → 302 → i.bucm.edu.cn/tp_nup/?ticket=ST-x
2) POST apim/sems-tp-nup/home/pingcurrent?service=<上面那个 URL>
        → {"code":401,"data":"https://cas.bucm.edu.cn/cas/oauth2.0/authorize?...&redirect_uri=..."}
3) GET  <authorize>（带 CASTGC）                      → 302 → tp_nup/cas.html?...&code=ST-y
4) GET  apim/sems-authc/oauth2/casToken/<code>/bucmnup?casDelegate=
        → {"code":200,"data":{"accessToken":"..."}}
```

**关键参数来源**（都在 `defaults/js/constant.js` 里，不是猜的）：
```js
gateway_url    = "https://i.bucm.edu.cn/apim"
contextpath    = gateway_url + "/sems-tp-nup"      // pingcurrent 在这个前缀下
contextpathAuthc = gateway_url + "/sems-authc"     // casToken 在这个前缀下
oauth_client_id = "bucmnup"
```

验证：native 拿到的 accessToken 长度 **927**，与手机上已有的完全相同（前缀一致）。

### 3.2 座位 ic-cookie 仍然拿不到（与 docs/13 结论一致）

走完 `toLoginPage` 预热 → CAS → `ic-web//auth/token` 后：
- 返回 **200 且 0 字节**
- `Set-Cookie` 里**没有** `ic-cookie`
- 但重定向 URL 上带出了一个 `uniToken`（JWT）

前端拿到 `uniToken` 后还要再换一次（用 localStorage / 请求头），这条没挖完。
**所以座位上保留了「网页补」这一个例外** —— 它是唯一会打开网页的地方，按钮文案写明「网页补」。

## 四、实现结构

| 文件 | 作用 |
|---|---|
| `DesLegacy.kt`（新，240 行） | `des.js` 的逐行移植。**不能换成 javax.crypto** |
| `CasCrypto.kt`（新） | 表单三件套 `seal()`（rsa / ul / pl），委托给 DesLegacy |
| `CasLogin.kt`（新） | CAS 登录：取登录页 → 解析 lt/execution → 提交 → 拿 CASTGC；错误解析 |
| `NativeLogin.kt`（新） | CASTGC → 四条凭证（门户 OAuth2 / 教务 / 一卡通 / 座位） |
| `LoginViewModel.kt`（新） | 登录流程状态。**没有 password 字段** |
| `LoginGateScreen.kt` | 改成学号密码表单 + 条件验证码 + 逐条进度 |
| `MainActivity.kt` | 去掉「跳 4 个网页」的串联，只留座位网页补登 |
| `Net.kt` | 新增 `getBytes()`（验证码图片） |

单测 113 → **136**（新增 DES 对拍 12 + CAS 解析 11）。

## 六、没做的 / 未验证

1. 🔴 **真实账号密码的端到端登录没跑过**。这必须用户本人在手机上做（我不能持有密码）。
   已验证的是：加密格式被接受、四条凭证的换取链路各自可用。
   **没验证的是「一次完整登录从输入到进体检页」这条串起来的流程。**
2. **验证码分支没有真实触发过**。当前账号登录表单不需要验证码；
   代码里做了 `captchaRequired` 判断和验证码图片加载，但没遇到真实要求。
3. `uniToken` 换 `ic-cookie` 没挖完。
4. 密码明文在内存里无法主动擦除（Kotlin `String` 不可变），只能保证不落盘。
5. 登录页 UI 是功能性的，没打磨。

## 七、给下一棒

- 如果学校改了登录页，**第一个要查的是 `des.js` 有没有变**（`login10.js` 里那行 `strEnc(u+p+lt,'1','2','3')`）。
  变了就重新对拍：node 跑新的 des.js，改 `DesLegacy.kt` 的测试期望值。
- `lt`/`execution` 一次一换，**不要缓存复用**。
- 失败 15 次锁 10 分钟，调试登录时千万不要循环重试。
- 门户 `accessToken` 一定走 OAuth2 码流，别指望 Set-Cookie。
