# 15 · 登录门禁（测试软件的正确入口）

> 交付时间：2026-11-21 夜　承接 `14-课表周视图.md`
> 本轮做完的：**App 打开即登录页；5 条必需凭证缺任何一条都进不去主界面**
> 一句话结论：**这个 App 的定位是「测试软件」（验底层接口与算法），入口必须先做凭证完整性门禁，否则跑出来的红点无法区分「接口坏了」还是「没登录」。**

---

## 一、为什么要有这层门禁

不是体验优化，是**刚需**。

轮次 2 的教训：所有学校登录态过期时，20 个探针全红。当时无法判断这 20 个红点是
「学校接口改坏了」还是「压根没登录」—— 白排查了一轮。

所以规则变成：**凭证不齐，不许测。** 缺任何一条必需凭证，App 只显示登录页。

> 用户定位（2026-11-21 明确）：现在不做产品功能，这个 App 只用来验底层接口和算法，
> UI 排布等后面再谈。所以默认落地页也从「首页四卡」改成了「数据体检」。

## 二、凭证清单（6 项，5 条必需）

| # | 凭证 | 必需 | 从哪来 | 缺了去哪补 |
|---|---|---|---|---|
| 1 | 门户 `accessToken`（JWT） | ✅ | 门户登录（cookie `accessToken`，path `/tp_nup`） | PORTAL |
| 2 | CAS `CASTGC` | ✅ | 门户登录时**顺带**保存 | PORTAL |
| 3 | 教务 `JSESSIONID` 整串 | ✅ | 教务登录（CAS SSO） | JW |
| 4 | 一卡通 `servicehall` | ✅ | 一卡通登录（CAS SSO） | ECARD |
| 5 | 一卡通 `openid` | ❌ **可选** | 落地页隐藏 input | ECARD |
| 6 | 图书馆 `ic-cookie` | ✅ | 座位预约平台登录 | SEAT |

### 2.1 为什么 `openid` 不做硬门槛

它是**派生值**（一卡通落地页里的 `<input id="openid">`），WebView 抓取时机不对就可能拿不到。
设成硬门槛的后果是：用户明明登录成功，却永远过不了门禁 —— 软件直接变砖。

而且它本来就会自愈：`HomeViewModel.refreshCard` 在 `openid == null` 时会重新走一遍一卡通登录。

### 2.2 为什么 JWT 过期算「没有」

严格按字面，「过期」≠「不存在」。但过期凭证用不了：待办、应用清单、消息接口一律 401。
放它进去，跑出来的红点又回到「分不清真假」的老问题。

所以门禁判定是 **「存在 且 未过期」**（只有 JWT 能判过期，因为它带 `exp`；CASTGC /
JSESSIONID / ic-cookie 都是不透明字符串，判不了）。

代偿：JWT 只有 4 小时，用户每 4 小时要重登门户一次。这是 CAS 门户的既定现实，不是本设计引入的。

**反例也留了路**：`jwtRemainingMs == null`（token 存在但解析不出 `exp`）时按「有值」处理，
不把一个畸形 token 当成过期把人挡在门外（有单测钉住）。

## 三、三种补齐方式

| 方式 | 场景 |
|---|---|
| **一键补全缺失** | 常规路径。按 PORTAL → JW → ECARD → SEAT 顺序自动串起来 |
| **单项「去登录」** | 只差某一条（比如座位 cookie 掉了） |
| **手工粘贴** | 某些凭证只能从别处捞（浏览器里已有的 cookie），门禁必须留这条路，否则站点一变更整个 App 就进不去了 |

### 3.1 一键补全的串联逻辑

门户必须第一个：它登录时顺带把 `CASTGC` 存下来，**后面三个目标全靠 CAS 单点自动过**，
用户基本只需要等页面跳转。

自动串联的两个刹车（否则会把用户困在弹窗循环里）：

1. **只认 `RESULT_OK`** —— `LoginWebViewActivity` 的「完成」按钮现在 `setResult(RESULT_OK)`；
   用户按系统返回键退出是 `CANCELED`，串联立即停。
2. **同一个目标不连试两次** —— 记录 `lastTried`，如果返回后「下一个该补的目标」还是它，
   说明这次没进展，停下让用户手动处理。

## 四、实现要点

| 文件 | 作用 |
|---|---|
| `Credential.kt`（新，~190 行） | 纯逻辑：`Snapshot` → `Audit`。**不碰 Android**，可 JVM 单测 |
| `CredentialGateTest.kt`（新，~180 行） | 18 个单测：逐条缺失、JWT 过期/将过期/解析失败、目标优先级、openid 可选 |
| `LoginGateScreen.kt`（新，~330 行） | 门禁页 + `readCredentialSnapshot(ctx)` + 手工粘贴面板 |

| `LoginWebViewActivity.kt` | 新增 `newIntent()`（给 `registerForActivityResult` 用）；「完成」改为 `setResult(RESULT_OK)` |

是为了让纯逻辑文件不依赖 Android Activity 类。UI 层用 `Target.of(name)` 转回去。

## 五、踩到的坑

### 5.1 `launcher` 不能在它自己的回调里引用自己

```kotlin
val launcher = rememberLauncherForActivityResult(...) { res ->
    launcher.launch(...)   // ❌ Unresolved reference 'launcher'（val 还没初始化）
}
```

编译直接失败。解法：回调里只置一个 `pendingLaunch` 标记，由 `LaunchedEffect(pendingLaunch)` 真正启动。

### 5.2 「一键补全」必须有刹车

第一版没有 `lastTried`，如果某个站点挂了（cookie 抓不到），返回后 `nextTarget` 不变，
会**无限重新弹出登录页**。加上「同一个目标不连试两次」才安全。

### 5.3 `LoginWebViewActivity` 的状态栏重叠（未修）

传统 View 布局没处理 WindowInsets，标题「数智北中医」被系统状态栏压住一半。
按用户「UI 排布后面再做」的要求，本轮不修，记在这里。

## 七、没做的 / 未验证

1. **真实登录全流程没走通** —— 登录需要输学号密码，这是红线（不代登录），
   只能由用户本人在手机上完成。所以「一键补全」串完 4 个目标后的最终放行，
   **本轮没有端到端证据**，只有逐条的单元与人工验证。
2. **手工粘贴→保存→放行** 这条链没实测（只验证了面板能展开）。
3. **凭证过期的其他几条判不了**（CASTGC / JSESSIONID / ic-cookie 都不透明）。
   现在只能靠「实际调用失败」发现，门禁不会提前拦。
4. 门禁页 UI 是功能性的，没有打磨（用户要求 UI 后排）。
