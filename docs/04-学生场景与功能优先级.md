# 04 · 学生场景盘点与功能优先级（MVP 依据）

> 依据：`docs/02-数智北中医架构.md`（接口实测）、`docs/03-应用可达性矩阵.md`（163 应用 + 30 系统体检）、`docs/01-公开站点盘点.md`（公开数据源）、`docs/05-可行性与合规.md`（合规边界）
> 目标读者：项目立项 / 产品设计 / 开发排期

---

## 0. 一句话结论

**学生真正每天要用的，只有 7 件事；学校已经把其中 5 件的入口塞进了微信企业号，但每一件都要跳 2–4 层。**
ubcm 的价值不在于"新功能"，而在于**把分散在 6 个系统里的 7 件事，收敛成 1 个页面**。而这件事的合法性，取决于它是不是"只处理用户自己的数据"。

## 3. 功能优先级（P0 / P1 / P2）

### P0 —— 没有它就不叫校园 App（首版必做）

1. **今日课表 / 下一节课倒计时**（数据源：教务课表，已有 `courses.json` schema 与解析规则）
2. **通知公告聚合**（官网 HTML 抓取，零登录门槛，先把"信息四散"解决了）
3. **校历 / 教学周 / 考试倒计时**（本地计算 + 门户日程接口）
4. **统一入口页**：教务 / BB / 一表通 / 后勤 / 图书馆 的**快捷跳转**（不重做，只收敛）

> P0 的共同特征：**要么零登录，要么数据源已探明**。首版不碰"需要长期维持登录态"的写操作。

### P1 —— 有用但依赖登录态

5. 成绩查询与出分提醒
6. 考试安排与提醒
7. 空教室查询
8. 待办 / 消息（门户 JSON 接口）
9. 体测预约

### P2 —— 差异化 / 需要校方或逆向

10. 跟师 / 跟诊记录（岐黄班特色，PC 表单移动化）
11. 图书馆借阅
12. 报修
13. 一卡通（**只能做"跳转企业微信"**，iOS 不设计 NFC —— 学校官网明示不支持）

### 明确不做（负面清单）

- ❌ 一卡通 NFC / 刷卡模拟（学校明示 iOS 不支持，且合规无解）
- ❌ 代登录 / 要求用户输入密码（见 05 文档：刑事风险，有判例）
- ❌ 校园社交 / 表白墙（无数据源、审核风险）
- ❌ 重做 133 个一表通流程（同一个平台的实例，做导航即可）

## 4. 差异化：凭什么用 ubcm 而不是微信企业号？

| 维度 | 微信企业号现状 | ubcm 能做的增量 |
|---|---|---|
| 入口 | 企业微信 → 工作台 → 应用 → 二级菜单（3–4 层） | **一屏直达**（课表 + 通知 + 待办） |
| 课表 | 教务系统的 JSP 表格，无提醒 | **下一节课倒计时 + 桌面小组件** |
| 通知 | 各系统各发一遍 | **聚合去重 + 按学院/班级筛选** |
| 跨平台 | 只有微信内（iOS/Android 通用但都困在微信） | **原生客户端**，可离线、可推送、可深链 |
| 岐黄班特色 | 跟师记录只有 PC 表单 | **跟师/跟诊移动化**（本校唯一） |

> 这不是"替代"，是"**在微信够不到的地方补位**"：原生推送、离线课表、桌面组件、深链、跨系统聚合。

## 5. 一个残酷但必须说清的前提

以上 P1/P2 全部依赖**用学生自己的账号登录**。而 05 文档给出的结论是：

- 「用户同意」≠「学校授权」，第三方长期代持登录态有刑事判例（武昌区 2024-12，Cookie 提供者以从犯处理）
- 个人身份**无法完成「教育移动应用提供者备案」**（主体须企业/社会组织）→ 公开上架这条路对个人基本关死
- 唯一低成本合法路径：**「校内自研自用」使用者备案**（京教信〔2024〕13 号 §18），代价是不能公开上架、不能对外校、不能收费

**所以本项目的真实形态有三种，必须先选一种：**

| 形态 | 描述 | 合规 | 上架 | 建议 |
|---|---|---|---|---|
| A. 个人学习工具 | 数据只在本机，用户自己登录自己看，类似"课表 App" | ✅ 风险最低 | 可尝试（需中性命名 + 非官方声明） | **推荐作为 MVP** |
| B. 校内自研自用 | 走网信办备案，仅校内分发（TestFlight / 内测 APK） | ✅ 可行 | 不上公开商店 | 想做"全功能版"就走这条 |
| C. 公开平台 | 面向全部学生提供账号代管 | ❌ 踩红线 | 需要企业主体 + 学校授权 | **不建议** |

## 6. 下一步建议（给立项）

1. **先和网信办谈**（数字与智慧校园建设中心，和平街 64286388 / 良乡 53911845）：问三件事 —— ①是否允许学生自研工具走「自研自用」备案；②CAS 是否对校内项目开放 OAuth；③一卡通/缴费是否有对内接口。**这三个答案决定项目上限。**
2. **MVP 按形态 A 做**：课表 + 通知 + 校历 + 跳转，不碰写操作、不代管密码。
3. **技术栈**：Kotlin/Compose（复用 KechTable 的课表渲染与胶囊经验）+ SwiftUI；课表解析复用 `bucm-jw-ops` skill 的规则。
4. **数据层**：能走公开的就走公开（通知公告、新闻）；必须登录的，**用户在自己的设备上登录、数据不出设备**。
5. **一卡通、缴费、BB 一律不做原生**，做"跳转 + 说明"，避免白做。
