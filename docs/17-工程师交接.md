# 17 · 工程师交接（需求 → 提示词）

> 交接时间：2026-11-24。给**需求分析 / 提示词工程师**看。
>
> **你的角色**：用户会跟你描述需求，你**不写代码、不改仓库**。
> 你的产出是**一份精准的开发提示词**，交给下一个写代码的 Agent 去执行。
>
> 所以你需要两件事：**① 搞清楚项目现在有什么；② 把用户的话翻译成可执行、可验收的提示词。**
> 这份文档就是为这两件事写的。

---

## 一、项目定位（先记住这一句）

**这是一个测试软件，不是产品。**

它的存在意义是**验证底层接口通不通、算法对不对**，UI 排布是后面才做的事。
用户（同学，北中医岐黄班 2026 级）反复强调过这一点。

- 已完成的模块都是**能跑、能验、能出数据**为准，不追求好看
- 但图书馆座位图是个例外：用户明确要求按比例重绘，那一块是被当成"要看的东西"在做
- 判断一个需求属于哪类，见 §四 4.1

**技术形态**：Android / Kotlin + Compose / **零第三方运行时依赖**（只有 Android SDK + org.json）。
本地优先：数据只存本机，不代登录、不托管凭证。

## 三、能力边界（决定需求能不能接）

### 3.1 技术红线（绝对不能碰）

| 红线 | 说明 |
|---|---|
| 🔴 不代登录、不存密码 | 密码只能作为函数入参活一次，不写 prefs、不写日志、不进 State |
| 🔴 不破解验证码 | 学校加的滑块是有意的人机验证，绕过不属于"技术攻坚" |
| 🔴 不做脚本抢座 | 让 App 自动挑最快空座就是抢座 |
| 🔴 写操作必须三段式 | prepare（复查）→ commit（只发一次）→ readback（核对，不确定就返回"未知"，**不升级为成功**） |
| 🔴 不提交任何真实凭证 | JWT / CASTGC / cookie / 学号密码，一律不进 git |

### 3.2 已知缺口（用户可能提的需求会落在这里）

| 缺口 | 现状 | 备注 |
|---|---|---|
| 座位凭证几小时就过期 | 过期后所有 `/ic-web` 返回 `code:300`，看起来像"接口异常" | 门禁只看本地有没有值，不看服务端认不认 |
| 红色座位（被占）从未在真机出现过 | 逻辑有单测，视觉没确认 | 需要挑一个有预约的日期才能看到 |
| 双指缩放未用真手指验证 | 锚点公式已实现 | adb 不支持多指，只能人测 |
| App 内预约未真实执行过 | UI 和链路都通了 | 会真占座，红线要求用户自己点第一次 |
| 长桌桌面位置是推断 | 画在座位下方 | 官方图个别长桌在上侧 |
| 静默补齐座位 cookie 不可行 | 进座位路由弹滑块 | 只能人工过一次 |
| 门禁不校验凭证是否仍有效 | 只看本地有没有 | 每次启动都校验会拖慢 |

### 3.3 明确"不做"的

- 不做离线缓存同步（本地优先，无后端）
- 不做多用户 / 共享
- 不公开上架（个人无法完成教育应用备案）
- 不做 UI 美化（除非用户明确要求，座位图那次是例外）

## 四、怎么把需求变成提示词

### 4.1 第一步：判断需求类型

| 类型 | 特征 | 提示词重点 |
|---|---|---|
| **A. 修 bug** | "XX 不对 / 显示错了 / 拿不到" | 复现条件 + 期望行为 + 相关文档 + 验收方式 |
| **B. 调参数/改视觉** | "太大了 / 颜色不对 / 间距不对" | **给出精确数值或比例**，不要用"好看一点" |
| **C. 新增功能** | "我想加一个…" | 数据源（哪套接口）+ 红线检查 + 是否需要写操作 |
| **D. 重做** | "重做 XX" | 先问清楚哪些保留、哪些推翻 |
| **E. 查/验证** | "看看 XX 能不能用" | 明确"只读，不要改代码" |

**最容易出错的是 B**：用户说"桌子大一倍"，如果不追问方向，Agent 会去放大水平——
但水平方向已经填满了，一放就重叠。**必须先把可测量的现状摆出来**（见 §4.4 示例）。

### 4.2 提示词模板

```markdown
# 任务：<一句话概括>

## 背景
<用户原话 + 你理解后的重述>
<相关文档：docs/XX §YY>

## 现状（必须写清楚，Agent 不该重新调研）
<关键数值/行为。例：三层南区 x 跨度 92%，画布 1080px，一个座位 9px>
<已知限制。例：水平方向一桌总宽 = 相邻桌中心距，不能再放大>

## 要做什么
1. <具体动作>
2. <具体动作>

## 不要做什么
- <红线相关>
- <明确排除的范围>

## 验收标准
- [ ] <可验证的条目，例：三层南区命中 21 桌，最右侧 3 张四人桌分开>
- [ ] 单元测试全绿（`./gradlew :app:testDebugUnitTest`）
- [ ] 真机/模拟器截图

## 收尾要求
- 读 `AGENTS.md` 的日志与提交规则
- `DEVLOG.md` 追加本轮记录（含"没做的 / 未验证"）
- 提交信息用中文，首行概括改动
```

### 4.3 必带的四样东西

1. **读哪几份文档** — 不写的话 Agent 会重新调研，浪费半小时以上
2. **现状数值** — 尤其是"已经试过、不行"的方向（否则会重蹈覆辙）
3. **验收标准** — 最好是**数字**（"命中 21 桌"而不是"看起来对"）
4. **红线提醒** — 涉及写操作/密码/验证码时必须写

### 4.4 示例：同一个需求的好/坏提示词

**用户原话**：「每张桌子大一倍，然后上下桌间距缩小」

**❌ 坏的提示词**：
> 把座位图里的桌子放大一倍，上下间距缩小。

问题：Agent 会把 UNIT 乘 2 → 水平方向一桌总宽 7.46% > 相邻桌中心距 3.73% → **桌子互相压住**。

**✅ 好的提示词**：
> ## 现状
> 座位图用单位制（1 单位 = 0.746 百分比）：
> - 水平方向真实间距 3.73，一桌总宽正好 3.73 → **已填满，不能再放大**
> - 垂直方向真实行距 3.9，4 行桌只占 4.1%（真实跨度 11.7%）→ **只占 35%，空得厉害**
>
> 所以"桌子小"实际是垂直方向被压扁（行缝按 0.5 单位排）。
>
> ## 要做
> 把 `ROW_GAP` 从 0.5 单位改成 1.5 单位（`DeskGeometry.kt`），
> 使 4 行桌长度从 5.5 单位变成 8.5 单位（1.55 倍）。列缝 `GAP` 保持 0.5 不动。
>
> ## 不做
> 不要动 `UNIT` 和 `TABLE_WIDTH` —— 水平方向放大必然重叠。
>
> ## 验收
> - 4 行桌长 = 8.5 单位、行缝 = 1.5 单位（`DeskGeometryTest` 有断言）
> - 上下间隔占图高约 7.5%（官方图 8.3%）
> - 单测 177 全绿

### 4.5 追问清单（用户说得含糊时）

| 用户说 | 要问清 |
|---|---|
| "不好看 / 不协调" | 具体是哪一项：位置、大小、颜色、间距？给个比例或数值 |
| "和官方图不一样" | 哪个区域、哪个位置？最好让用户截图标注 |
| "接口异常" | 哪个页面、什么提示文字？能否抓 logcat |
| "加个功能" | 数据从哪来？要不要写操作（涉及红线）？ |
| "优化一下" | 优化什么指标：速度、准确率、还是视觉效果？ |

## 五、交付前自检

写完提示词，过一遍：

- [ ] **指明文档**：Agent 知道该读 `docs/XX`，不用重新调研
- [ ] **摆出数值**：尤其是"已试过不行"的方向
- [ ] **验收可测**：是数字或明确行为，不是"看起来对"
- [ ] **红线覆盖**：涉及密码/验证码/写操作时有提醒
- [ ] **范围收敛**：写明"不要做什么"，防止 Agent 擅自扩大改动
- [ ] **收尾要求**：日志 + 测试 + 提交规则

## 七、一句话总结

**项目已经能跑通「登录 → 拿数据 → 看座位/课表 → 预约」的完整链路，算法层有 177 个单测兜底。**
