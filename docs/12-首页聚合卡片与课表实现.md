## 三、三种登录态的寿命不同（这是首页必须处理的事）

实测这轮发现：**它们不是一个东西，不能用一个「已登录」表达**。

| 凭证 | 寿命 | 失效后谁受影响 |
|---|---|---|
| 门户 JWT（`accessToken`） | **4 小时** | 未读待办、应用清单、消息 |
| CAS `CASTGC`（TGT） | 数小时~天，**会过期** | 重新换 servicehall / 重新登教务 |
| 教务 `JSESSIONID` | 会话级，最短 | 课表刷新 |
| 一卡通 `servicehall` | 长效（数小时，常比 CASTGC 活得久） | 余额/流水 |
| 座位 `ic-cookie` | 长效 | 座位 |

**实测证据**：JWT 过期后（`门户过期`），一卡通余额仍能正常拿到 ￥13.17 —— 因为 `servicehall` 会话还在缓存里。
所以首页顶部做成**三态**：`已登录` / `门户过期` / `一卡通在线` / `未登录`，而不是二元。

### 3.1 一个已修复的坑

`refreshCard(force)` 原来在 `force=true` 时先 `Session.clearEcard()`。但 servicehall 会话比 CASTGC 活得久，
**一点刷新就把还能用的会话清掉了，余额直接消失**。已改为：先用缓存会话，失败了才重登。

### 3.2 静默续期：走不通（实测）

试过用 CASTGC 直接换新 JWT（`GET cas/login?service=.../tp_nup/` 带 `Cookie: CASTGC=TGT-...`），
CAS 返回 **200 登录页 + `Set-Cookie: CASTGC=; Max-Age=0`** —— 它判定 TGT 失效并主动清除。
所以**没有可靠的后台静默续期路径**，JWT 过期后只能让用户走一次 WebView 登录。这是设计约束，不是没实现。

## 四、课表算法（容易算错的三件事）

### 4.1 周次锚点

```
第 1 周周一 = 2026-09-07（本学期）
week = floorDiv(日期 − 首周周一, 7) + 1
```

- **必须用 `floorDiv`**：Kotlin 的 `/` 向零取整，开学前 6 天会被算成「第 1 周」（单元测试抓到过，是第一版真 bug）。
- 锚点存在 `Session.loadFirstWeekMonday`，默认 `Timetable.DEFAULT_FIRST_WEEK_MONDAY`。
- 🔴 **每学期必须更新这个常量**，否则「第几周 / 下一节课」全错，而且错得很隐蔽（会算到不存在的课）。

### 4.2 大节 → 小节时间推算

教务只给**大节**（`lstJx0415zb`：`第1-2节 08:30–10:00`），但课可以是单节或跨大节（`第1-3节`）。
做法：把每个大节时长**平均分配**给它覆盖的小节。

实测校验：大节 1-2 = 90 分钟 / 2 = 45 → `第1节 08:30–09:15`、`第2节 09:15–10:00`，与官方导出的 12 小节作息逐条一致（有单测断言）。
拿不到大节表时回退 `Timetable.FALLBACK_SLOTS`（良乡作息硬编码）。

### 4.3 下一节课

从今天起往后扫 7 天：每天按周次过滤 → 按开始节次排序 → 跳过已结束的（`end <= now`）→ 第一个命中就是它。
正在上的课 `phase=ONGOING`（首页显示「还剩 N 分钟」），否则 `UPCOMING`（「还有 N 分钟」）。

⚠️ 不要按「两节一组」分组（3–5 节的课会被切错），要按节次高度绝对排版——这条是 KechTable 踩过的，本次已按节次绝对时间实现。

## 八、平板真机测试记录（2026-11-21 凌晨）

设备：小米平板 9 Pro Max（`M367FC` / Android 17 / HyperOS 4.0.16.0 / 3408×2272 / USB 通道）。
第一次在**真机**上跑，暴露了 5 个模拟器上没出现的问题，全部已修：

### 8.1 大屏布局（不修就是「一整条横带」）

- 首页/体检页都加 `windowInsetsPadding(WindowInsets.safeDrawing)` —— 否则标题被状态栏压住
- 内容 `widthIn(max = 640/720.dp)` 并 `Alignment.TopCenter` 居中，底部按钮同样限宽
- 截图对比：`ubcm-pad-01.png`（修前）→ `ubcm-pad-02.png`（修后）

### 8.2 登录器只抓 3 个目标，缺「教务」

原实现没有教务入口，而课表刷新必须要有 jw 域的 JSESSIONID。已加 `Target.JW`，
并把一卡通登录时落地页的 `openid` 一起存下（`Session.saveEcard`。

### 8.3 🔴 轮询查错了 cookie 域（登录成功也存不下来）

`CookieManager.getCookie(url)` 必须传 **cookie 真正所在的域 + path**，不是登录入口的 URL：

| 目标 | 登录入口 | cookie 真实位置 |
|---|---|---|
| 门户 | `cas.bucm.edu.cn/cas/login?...` | `https://i.bucm.edu.cn/tp_nup/`（path=`/tp_nup`） |
| 教务 | `cas.bucm.edu.cn/cas/login?service=jw...` | `https://jw.bucm.edu.cn/jsxsd/` |

首版传的是 CAS 入口 URL，导致 `getCookie` 永远返回 null —— **登录明明成功，凭证却一条都存不下来**。
先修了域、仍然失败，因为 `accessToken` 的 **path 是 `/tp_nup`**，用 `https://i.bucm.edu.cn/`（path=`/`）查也不匹配。
所以 `Target` 里加了 `cookieHost` 字段，写死带 path 的完整 URL。

> 验尸方法：在登录器顶部状态栏直接打印 `getCookie(cookieHost)` 的字节数。页面白屏时这是唯一可见的通道，比猜快得多。

### 8.4 🔴 教务站 TLS 证书链不完整（真机必炸）

```
openssl s_client -connect jw.bucm.edu.cn:443
  0 s:CN=*.bucm.edu.cn  i:…GeoTrust G2 TLS CN RSA4096 SHA256 2022 CA1
  Verify return code: 21 (unable to verify the first certificate)   ← 只有 1 张
```

对比门户 `i.bucm.edu.cn` 发 3 张（叶子+中间+根），所以门户一直正常。
macOS/浏览器会走 AIA 自动补中间证书，**Android 的 TrustManager 不会**，于是真机上：
`SSLHandshakeException: Trust anchor for certification path not found`。

修法见 `Tls.kt`：内置那张公共中间证书（`res/raw/bucm_intermediate.cer`），
系统校验失败时**把中间证书补进链里重试**。不是跳过校验，补完仍然失败就照常抛。
`MainActivity.onCreate` 里 `Tls.install(this)`。

> ⚠️ 这个坑在模拟器上**没暴露**（模拟器的证书策略或 DNS 命中不同节点），只在平板上炸。
> 表现是首页「还没有课表」+ `files/timetable.json` 不生成，非常容易被误判成「没登录」。

### 8.5 🔴 WebView 白屏：Compose `AndroidView` 的合成问题

现象：登录器整片白，但 `document.title` 正常、`body.innerText` 有 1448 字符、
`Page.captureScreenshot` 直接超时（合成层无输出）。

排查与取舍：
- `weight(1f)` 修正布局 —— 无效
- `setLayerType(LAYER_TYPE_SOFTWARE)` 强制软件渲染 —— **无效**
- **改成传统 `setContentView` 布局（`LoginWebViewActivity` 不再用 Compose）—— 解决**

结论：**WebView 不要放进 Compose 的 `AndroidView`**（至少这台设备 + Android 17 + WebView 150 不行）。
换掉之后门户首页完整渲染（`ubcm-pad-18-webview-native.png`）。

> 这个缺陷如果不修，新用户首次登录（要输密码 + 短信验证码）会被彻底卡死 ——
> 虽然凭证抓取在后台照常工作，但用户看不见输入框。
