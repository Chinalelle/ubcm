## 三、认证：一个关键发现 + 一个仍未解的点

### 3.1 `doAuth` 的「url 缓存」是什么（已破解）

`11-交接文档` 里写「`/authcenter/doAuth/` 需要 URL 缓存预热（`10011 url缓存无数据`）」，但没说怎么预热。
在浏览器里观测真实跳转，完整链路是四步：

```
1. GET /ic-web/auth/userInfo                                   ← 判断未登录
2. GET /ic-web/auth/address?finalAddress=...&consoleType=16    ← 问服务端用哪种认证
3. GET /authcenter/toLoginPage?redirectUrl=<.../ic-web//auth/token?uuid=<32hex>...>&extInfo=<uuid前10位>
                                                                ← 这一步把 redirectUrl 按 uuid 缓存到服务端
4. GET cas.bucm.edu.cn/cas/login?service=.../authcenter/doAuth/<另一个32hex>
```

所以「url 缓存」就是第 3 步 `toLoginPage` 写进去的；随机 id 由**前端生成**（32 位 hex，每次不同）。
直接拿 CASTGC 去请求 `/doAuth/<id>` 而不先调 `toLoginPage`，就会得到 `10011 url缓存无数据`。

> 这是本次破解的**真正阻塞点**，已实测：按 1→4 顺序构造，能一路 302 走到
> `/ic-web//auth/token?uuid=...&uniToken=<JWS>&extInfo=...`（200）。

### 3.2 ⚠️ 但仍然没拿到 ic-cookie（纯 native 未成）

走完上述 4 步后，`auth/token` 返回 **200 但 0 字节、无 `Set-Cookie`** —— 没有 ic-cookie。
而在 App 的 WebView 里走同一个流程，`kjyy.bucm.edu.cn` 域下**有** `ic-cookie`（36 字节，UUID 形态：
`f231f38f-5aa9-4ec0-a921-4203b783039b`，`path=/`）。

结论：**ic-cookie 是前端 JS 在那之后才换来的**（不在 `auth/token` 的响应头里）。
未定位到具体是哪一步 —— 试过在 WebView 里 hook `fetch`/`XMLHttpRequest`（含
`Page.addScriptToEvaluateOnNewDocument` 持久注入）后硬导航到座位预约路由，**抓不到任何 `/ic-web/` 请求**，
怀疑该页组件被缓存、或 hook 时机不对。

**所以当前 IC 登录唯一可靠路径 = WebView**：
`数据体检/登录 →「图书馆座位」` → 抓到 ic-cookie 存进 `Session.seatCookie`。
实测这一步是通的（本次就是用这条路拿到的 cookie，随后三个接口全部 200）。

## 六、2026-11-21 追加：「我的预约」已实现 + 自动化预约的可行性判断

### 6.1 路由的前缀坑（先记下来）

移动端 Vue Router 的**真实路由没有 `/ic/` 前缀**。之前按 `/ic/seatPredetermine` 试了半天全部 0 请求，正确的是：

```
#/seatReserve     座位预约     → POST /ic-web/captcha/get（要验证码）
#/reserveRecord   预约记录     → GET  /ic-web/reserve/resvInfo?...
```

路由表可以直接从页面里读出来（调试用）：
```js
document.querySelector('#app').__vue__.$router.options.routes.map(r => r.path)
```

### 6.2 「我的预约」接口（已实现）

```
GET /ic-web/reserve/resvInfo
    ?beginDate=yyyy-MM-dd&endDate=yyyy-MM-dd
    &page=1&pageNum=999&orderKey=resv_begin_time&orderModel=desc
```
- `pageNum` 在这套接口里当**每页条数**用（999 = 全部）
- 关键字段：`resvDate`(20261119) / `resvBeginTime`、`resvEndTime`（**UTC，要 +8 小时**）/
  `resvCheckTime`（签到时间）/ `resvStatus`(1217) / `resvDevInfoList[0]`：
  `devName`（座位号，如 `5WB193`）、`roomName`（五层西B区）、`labName`（图书馆五层）、`roomId`、`labId`
- 实测 11–17 条记录全部 `resvStatus=1217`

> ⚠️ **不要用 1217 去猜状态**：只有一种样本，猜错就是骗人。
> `SeatApi.Resv.statusText()` 用「有没有签到 / 有没有结束 / 和当前时间的关系」推：
> 已结束 / 使用中 / 待签到 / 已签到 / 已预约。

UI 实测见 `ubcm-lib-07-resv.png`：进行中的置顶高亮，下面是最多 6 条历史。

### 6.3 自动化预约：能做，但**卡在滑块验证码**，不建议硬做

写接口已经定位到（chunk 里明确）：
```js
POST reserve/seat        // 提交预约（params 里带 roomId/devId/时间段）
GET  /reserve/seatArea   // 查座位图（参数含 date，其余未试出）
```

但进 `/seatReserve` 页面时前端第一件事是：
```js
POST /ic-web/captcha/get   { captchaType: "blockPuzzle", ... }   // AJ-Captcha 滑块
```
JS 里组件名是 **`VerifySlide`**，配套 `POST /ic-web/captcha/check`。

**结论：全自动预约 = 必须先破解滑块验证码。**

判断（这条要交给下一棒，别再走弯路）：
1. 验证码是学校有意加的人机验证，破解它属于**绕过安全措施**，不是"技术难度"问题；
2. 图书馆预约规则通常禁止脚本占座，触发风控后可能连带影响账号/违约记录；
3. 项目红线是「只读取自己的数据 + 写操作克制」，自动化抢座已经越出这条线。

**因此本项目不做验证码破解、不做全自动抢座。**

### 6.4 替代方案（价值 90%、风险 0）

按这个顺序做，体验接近自动化，又不碰验证码：

1. ✅ **我的预约**（已做）：进 App 就能看占了哪个座、几点到几点、是否要签到。
2. **座位图只读预览**（未做）：`GET /reserve/seatArea` 只读，能显示"哪个座现在空着"。
   参数名 `date` 已确认对（错误从「参数缺失」变成「系统繁忙」说明进了业务层），其余参数待试出。
3. **一键直达**（已做）：`SchoolWebActivity` 打开官方页面，已是登录态，选座 + 手划验证码 + 提交。

体验上就是：App 里先看清哪儿有座、约过哪些 → 一键进官方页 → 手划一次 → 完成。
把"找信息"全自动化，只把"人机验证 + 最终提交"留给官方页面。

## 七、「点区域直接进选座页」已实现（2026-11-21 补充）

用户要的其实是「在 App 里点几下就能约」，不是脚本抢座。已做到：

**图书馆 → 展开楼层 → 每个区域行右侧「约 ›」→ 直接打开该区域的座位预约页**

实测（`ubcm-lib-12-final.png`）：点「五层南区」→ 页面直接是「座位预约」，标题栏显示区域名，
hash 为 `#/seatReserve?roomId=43`。

### 7.1 学校页面的两个路由坑（都踩过，记下来）

1. **冷启动不认 URL 里的 hash**：直接 `loadUrl("...mobile.html#/seatReserve?roomId=43")` 会落到首页。
   必须先加载 `...mobile.html`，等首屏完成再用 JS 切路由。
2. **`onPageFinished` 里立刻切也没用**：那时 Vue 还没 mount，改 hash 会被路由初始化覆盖。
   实测要**延迟 2.5 秒**，且优先用 `$router.push(path)`（比 `location.hash=` 可靠）：

```js
var vm = document.querySelector('#app').__vue__;
vm.$router.push('/seatReserve?roomId=43');
```

代码见 `SchoolWebActivity.applyRoute()`；`start(ctx, url, title, hashAfterLoad)` 多了一个参数。

### 7.2 为什么座位图不是原生画的

进 `#/seatReserve` 后前端**只发一个请求**：`POST /ic-web/captcha/get`（滑块图），
之后没有任何座位请求 —— 也就是说**验证码通过前，服务端不下发座位数据**。

所以「原生 Compose 画座位格 + 点一下提交」这条路的真实前提是：先在 App 里复刻 AJ-Captcha 滑块并过验证。
那既重又脆，而且等于把学校的人机验证搬进客户端。

**当前实现是在 App 内用 WebView 承载学校页面的座位图**：
用户看到的流程是「点区域 → 选日期时间 → 点座位 → 提交」，全程不离开 App，
只是最后那一段 UI 由学校页面渲染。这是既满足需求、又不碰验证码的做法。

### 7.3 预约规则（实测读出来的，很有用）

`GET /ic-web/reserve/seatArea?date=yyyyMMdd` 返回的每个区域带 `resvRule`：

| 字段 | 值 | 含义 |
|---|---|---|
| `earliestResvTime` | 1440 分钟 | **最早提前 24 小时** → 所以不能约当日（与用户说法一致） |
| `cancelTime` | 30 分钟 | 提前 30 分钟可取消 |
| `minResvTime` / `maxResvTime` | 30 / 1440 | 单次最短 30 分钟、最长 24 小时 |
| `timeInterval` | 5 | 时间粒度 5 分钟 |
| `earlyInTime` | 10 | 提前 10 分钟可签到 |
| `devRoomList` | 16 个 roomId | 该规则覆盖的区域 |

> 注意：`date` 传**当天**时 `resvRule` 是 `null`（窗口已关）；传明天起才有规则。
> 这也解释了为什么凌晨查座位图时 `children` 是空的 —— 不是周末不开放。

## 八、「找没人的大桌」——座位图聚类（2026-11-21 夜间，核心痛点）

用户真实需求：图书馆是**大桌（4/6 连座）和单人桌混排**，人少时想找一张**整桌空着**的大桌坐下。
学校页面只画点位，不给"哪几个座属于同一张桌"，所以这里用几何还原。

### 8.1 🔑 座位图接口（本轮最重要的破解）

```
GET /ic-web/reserve?resvDates=yyyyMMdd&roomIds=<单个区域id>&sysKind=8
```

- 参数名是**复数**：`resvDates` / `roomIds`，来自前端 `SeatReserve.handleGetSeat()` 源码
- `roomIds` **只接受单个值**，传逗号会报「请求参数错误」
- 返回该区域**全部座位**，含：
  - `devName`（5S077）、`devId`、`devStatus`（0=可约）
  - **`coordinate`："12.342857,84.055118"** ← 图上百分比坐标，聚类全靠它
  - `roomId/roomName/labId/labName`、`resvInfo`（该座位的预约，实测历史日期已被清理为空）
- 打开 `#/seatReserve` 页面本身会先要滑块验证码，但**这个查询接口不需要**——直接带着 ic-cookie 就能拉

> ⚠️ **服务端限流**：连续请求会返回 `{"code":1,"message":"请求频繁,请稍后重试"}`。
> 实测间隔 <300ms 必被拒。App 里每次请求间隔 350ms、失败再等 1.2s 重试一次。
> 五层 5 个区域扫完约 2–3 秒。

### 8.2 桌面聚类算法（`DeskFinder.kt`，纯函数 + 12 个单测）

```
1. 按 roomId 分组          ← 关键！见 8.3
2. 组内按 y 分行（容差 1.0）
3. 行内按 x 排序，间距 > 2.4 就断开 → 一组 = 一张桌
4. 过滤：组内座位数 ≥ 4 且全部 devStatus=0
5. 按连座数降序
```

依据（五层南区 164 座实测）：同一排的 y **完全相等**，同桌椅子的 x 间距稳定在 **1.94–2.17**，
桌与桌之间的间距明显变大（2.6–3.3）。阈值 2.4 正好切在真实桌界上。

实测输出（五层南区）：
```
13 连座 5S100–5S112 / 9 连座 5S077–5S085 / 8 连座 5S129–5S136 /
8 连座 5S157–5S164 / 5 连座 5S086–5S090 / 其余全是 1 座
```

> 已知近似：两张桌子紧挨着摆（间距仍 ≈2.0）会被并成一组。但那种情况下整组都空，
> 用户直接坐也不吃亏，不会误导。**双人桌也会被并进 4 连座**，如需更细可按 `devName` 编号连续性再切。

### 8.3 🔴 踩到的坑：跨区域坐标混算

第一版把五层 5 个区域的座位**合并后**一起聚类，结果切出了
「`5S077–5WB267`」「`5N017–5WB042`」这种跨区域的假桌子。

原因：**每个区域的 `coordinate` 是各自独立的坐标系**，不同区的点会重叠，
按 y/x 聚类自然串在一起。

修法：`findFreeDesks()` 入口先 `groupBy { it.roomId }`，每区独立聚类再合并。
并加了一条单测 `不同区域的座位不会被聚成同一张桌` 锁住它。

### 8.5 仍可改进

1. **按"整天空闲"还是"某时段空闲"**：`devStatus` 目前只反映"该座位这天是否可约"，

## 九、完整的「时段 → 空桌 → 简略图 → 预约」流程（2026-11-21 凌晨）

### 9.1 用户流程与实现

```
1. 选使用时段（上午 / 下午 / 晚上 / 全天，默认 08:30–22:00）
2. 按时段筛空桌：每张桌的每个座位都要在该时段无冲突
3. 空桌列表（按连座数降序）
4. 点一张桌 → 简略图：该桌座位按坐标排成一行，标「空 / 占」
5. 点某个座位 → App 内直接提交预约（三段式，不跳网页）
```

界面见 `ubcm-slot-03-desk.png` / `ubcm-final-flow.png`。

### 9.2 🔑 关键发现：**不需要验证码**（推翻了 §6.3 的判断）

之前看进 `#/seatReserve` 页面会先调 `POST /ic-web/captcha/get`，判断"预约必须过滑块"——**这个判断是错的**。

读 `SeatReserve.handleSubmit` 源码后真相是：

```js
if (this.sysConfig.resvCode === "1") { $refs.codeDia.show = true }   // 图形验证码
else if (this.sysConfig.resvCode === "2") { $refs.verify.show() }     // 滑块验证
else { this.sendData({...}) }                                         // 直接提交
```

而实测学校配置 **`sysConfig.resvCode === "0"`** → 走 else，**直接提交，没有任何人机验证**。
进页面时那次 `captcha/get` 只是预加载，`resvCode=0` 时并不使用。

提交接口与请求体（从 `handleSubmit` + `sendData` 反推，已实测接口存在且不需要验证码）：

  "resvMember": [53247],

### 9.3 写操作按三段式实现（`LibraryViewModel.reserveSeat`）

```
prepare  重新拉该区域座位表 → 确认这个座这个时段**现在仍然空着**
         + 拿 accNo；任一步失败就中止，绝不提交
commit   POST 一次，不重试
readback 再拉一次座位表 → 确认该座该时段已变成"被占"
         回读看不到 → 返回「结果未知」，**不升级为成功**
```

### 9.4 ⚠️ 风险提示（写在代码注释和 UI 里）

预约成功后学校会要求在 `earlyInTime`（10 分钟）内到馆签到，**逾期算违约**，会影响信用分。
所以 App 里点座位就是**真实预约**，不是"预演"。

我实现完这个流程后**没有替你点任何一次真实预约**——那会占掉明早的一个座位，
如果你不去就是一次违约。第一次请你自己点，确认无误后再日常使用。

### 9.5 已知边界

1. **日期固定为明天**：学校 `earliestResvTime=1440`（最早提前 24 小时），当日不可约。
   要支持"约后天/大后天"需要再加日期选择。
2. **`devStatus` 是整天口径**（实测未来日期全为 0），真正决定冲突的是 `resvInfo` 里的时段。
3. 只有五层被扫描；`devStatus`/`resvInfo` 的语义在跨天场景下还没长期观察过。
