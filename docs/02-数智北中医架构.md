## 0. 一句话结论

**「数字北中医」不是一个网站，而是一个"门户壳 + 统一认证 + 一堆外挂系统"的集成体**：

- 门户（`i.bucm.edu.cn/tp_nup`）本身是 jQuery + layui 的**传统多页应用**，前后端通过 `/apim/sems-tp-nup/**` 的 **POST JSON** 接口通信，登录态是一个 4 小时有效的 **JWT（存在 cookie `accessToken`）**；
- 门户里挂 **6 个模块**：门户首页（可配置卡片）、服务大厅（**979 条，但 88% 是 PDF 办事指南**）、应用中心（**163 个应用，其中 133 个是同一个"一表通"办事平台**）、消息中心、日程中心、你问我答；
- 真正的业务能力在**门户之外**：教务（jw）、Blackboard（bb）、轻新课堂（qxkt/qhz）、资助（zhzz）、后勤（zhhq）、缴费（jiaofei）各自独立，靠 **CAS 单点登录**串起来；
- 学校**没有官方 App、没有独立 m 站**；移动端主阵地是 **企业微信（appid `wx636e84444c7a2fdc`）+ 微信小程序平台（wxapp.bucm.edu.cn）**。
- 对 ubcm 的含义：**数据源是可用的（接口规范、字段齐全），但"移动端"这层要自己做**——这既是空白机会，也是它全部的工作量所在。

## 2. 统一认证体系（决定 APP 登录方案的关键）

### 2.1 链路

```
学生打开 i.bucm.edu.cn
  → 未登录：跳 cas.bucm.edu.cn/cas/oauth2.0/authorize?client_id=bucmnup&redirect_uri=.../tp_nup/cas.html
  → CAS 认证成功，回跳 https://i.bucm.edu.cn/tp_nup/cas.html?service=...&code=ST-346379-...
  → 门户后端换 token，种 cookie：accessToken / redirectURL / SubsiteInfo
  → 之后所有 /apim/sems-tp-nup/** 请求带 cookie
```

### 2.2 accessToken 是什么（已解出 JWT 结构）

字段（**注意含敏感信息**）：

```
sub=学号(20260000000)  user_uid=user_name=姓名  mobile=手机号
unit_uid / card_type / card_id（校园卡）  id_number（身份证号）
birthday  avatar_p_id / avatar_m_id / avatar_l_id（人脸照片 https://face.bucm.edu.cn/...）
iss / aud / resource_id / language / id_type / exp
```

- 有效期：**4 小时**（`exp` 实测 ≈ 登录时刻 + 4h）
- 存放：cookie `accessToken`（HttpOnly 未验证，页面 `document.cookie` 可读 → 说明**不是 HttpOnly**，XSS 可窃取，APP 侧要注意不要把它暴露给 WebView 里的第三方页面）

### 2.3 接口调用范式（已用 curl 实测验证）

```
POST https://i.bucm.edu.cn/apim/sems-tp-nup/<模块>/<方法>
Content-Type: application/json
Authorization: Bearer <accessToken>      ← 关键：走 header，不是 cookie
Body: {参数}
→ {"code":200,"msg":"操作成功","data":...}
```

**实测结论（重要）**：

| 请求 | 结果 |
|---|---|
| 无任何凭据调 `/bucm/fw/getUnitType` | **200 成功**（部门树是公开数据） |
| 无凭据调 `/bucm/appmarket/getMySubscribeApp` | `{"code":0,"msg":"未传递 access_token或Authorization 头信息"}` |
| 只带 `Cookie: accessToken=...` | 同样 `code:0` 拒绝（**服务端不认 cookie**） |
| 带 `access_token: ...` 自定义头 | 拒绝 |
| **带 `Authorization: Bearer <JWT>`** | **200 成功，163 个应用全量返回**（429 KB） |

→ 含义：**门户 API 是一个标准的 JWT 无状态网关，任何能拿到 JWT 的客户端都能直连**，不需要浏览器、不需要 cookie 罐。
→ 对 APP 的意义：只要解决"怎么拿到 JWT"（即 CAS 登录流），后面的数据层就是纯 REST，工程上很轻。
→ 安全含义：JWT 一旦泄露，4 小时内可全量读取该学生全部数据（含邮箱、待办、日程、身份证号）。客户端必须保护它。

页面内是 jQuery `Util.ajax` 封装（自动加 Bearer 头），参数序列化成 JSON POST。
另有 `/apim/sems-tp-nup/getToken` 返回一个短 token，用于 `getRecentQuery` 等查询接口。

### 2.4 其它可用通道

| 通道 | 证据 | 对 APP 的意义 |
|---|---|---|
| 企业微信 | 财务/采购的移动端地址是 `open.weixin.qq.com/connect/oauth2/authorize?appid=wx636e84444c7a2fdc&agentid=1000122` | 学校已有企业微信应用体系，**小程序/公众号 H5 是现成的移动端通道** |

## 3. 门户六大模块逐一拆解

门户顶部导航（6 项）：门户首页 / 服务大厅 / 应用中心 / 消息中心 / 你问我答 / 日程中心。

### 3.1 门户首页 —— 可配置卡片中心

- hash：`#act=sems-tp-nup_29827717`
- 首页不是写死的：`POST /homePage/sceneData` 返回**卡片模板 JSON**（`SCENE.TEMPLATE[]`，每项含 `WIDGET_NAME`、`WIDGET_SHOW_JSP`、`PAGE_ID`、权限位）
- 现有卡片：广告轮播、推荐应用、通知公告、新闻资讯、待办事宜、站内邮件、天气/日期（农历）、校园信息
- 相关接口：

| 接口 | 作用 |
|---|---|
| `/homePage/sceneData` | 首页卡片布局配置（12 KB） |
| `/home/getHomeCarousel` | 轮播（含 `AD_IMG_MOBILE` 移动端图） |
| `/bucm/appmarket/getBnuRecommendApp` | 推荐应用（5 个） |
| `/card/weather/getWeatherAndDate` | 天气 + 农历 |
| `/bucm/campusBucm/getBnuCampusPimPageInfo` | 校园信息流 |
| `/campus/information/card/getUrgentPimList` | 紧急待办 |
| `/task/getTaskInfo` | 待办任务 |
| `/bucm/oaemail/getInboxHome` / `haveRedPoint` | **站内邮箱收件箱 + 未读红点** |

> 启示：门户首页的"卡片中心"模式，正是 ubcm 首页该抄的架构 —— 服务端下发卡片配置，客户端按配置渲染。

| 人事服务 | 32 |
| 科研服务 | 172 |
| 财务服务 | 163 |
| 外事服务 | 125 |
| 网络服务 | 8 |

- **关键统计**：`PC_ACCESS_ADRESS` 里 `type=2`（本地文件）**864 条**，`type=1`（真实链接）仅 **115 条**
  → 服务大厅本质是**办事指南文档库**（PDF/Word），不是可操作的自助服务

**「常用网址」= 官方认定的 9 个核心系统**（这是 APP 功能骨架最权威的依据）：

| # | 系统 | 说明 |
|---|---|---|
| 1 | 本科教务管理系统（新） | 课表/成绩/考试/选课 |
| 2 | 北中医微课堂 | 乐享（lexiangla）平台 |
| 3 | 学校官网主页 | 新闻/通知 |
| 4 | 数字北中医 | 统一门户 |
| 5 | 校外访问 VPN | wEngine，校外必用 |
| 6 | BUCM 邮件服务系统 | 学生邮箱 |
| 7 | 校园网认证用户自助服务 | 上网账号/缴费 |
| 8 | Blackboard（BB） | 课程平台 |
| 9 | 图书馆 | 超星门户 |

**一卡通（关键缺口，已查明）**：`xxzx` 官方指南《【充值服务】校园一卡通如何充值》写明三种充值方式 ——
① **「北京中医药大学微信企业号」→ e卡通模块 → 充值**（学生卡可用；充值后还要去圈存机"领款"）

③ 现金（校园卡管理中心 / 自助现金机）

**人脸识别 / 门禁**：同样是「通过企业微信（企业号）自助采集」，无独立网页端。

> 结论：**学校的移动端能力全部沉淀在微信企业号里**。这不是"还没有 APP"的空白，而是"已经有了一个不是 APP 的移动端" —— ubcm 要回答的第一问题不是"做什么功能"，而是"凭什么让同学从企业号迁移过来"。

## 5. 移动端现状（用户要做的"苹果/安卓 APP"面对的真实格局）

| 项 | 现状 | 证据 |
|---|---|---|
| 官方独立 App | **没有** | m/wap/app/mobile.bucm.edu.cn 全不可达；官网无「客户端」入口 |
| 官方 m 站 | **没有** | 官网是响应式 HTML（`.mobile_header`/`.only_mob`） |
| 微信小程序 | **存在**（平台 wxapp.bucm.edu.cn 可登录） | 具体小程序清单/AppID 未公开获取到 |
| 企业微信 | **是主要移动阵地** | 教务/财务/采购的移动入口都是企业微信 OAuth（appid `wx636e84444c7a2fdc`） |
| 门户自身移动适配 | **弱** | tp_nup 未检测到 viewport/mobile 专用 JS；门户 6 模块是给大屏设计的 |
| 移动端唯一官方载体 | **「北京中医药大学微信企业号 / 企业微信」** | 一卡通充值、人脸采集、门禁、教务移动端、缴费全部走它 |
| 移动端 H5 覆盖 | 142 个地址，但多为 `workflow` 的 `m_` 页面 | 见 `docs/03-应用可达性矩阵.md`（并行任务） |

**iOS/Android 必须处理的硬约束**（来自公开站点侦察）：
- `http://qxkt.bucm.edu.cn:88/ve`（轻新课堂）— HTTP 明文 + 非标端口
- `http://jy.bucm.edu.cn`、`http://202.204.32.22/jypx` — HTTP 明文
- 这些若要 WebView 内嵌，iOS 需 `NSAppTransportSecurity` 例外，上架会被审核问询

## 6. 对 ubcm 的初步判断（待可行性分析合并）

1. **数据是够的**：门户接口规范、字段完整（应用清单、服务清单、待办、日程、邮箱、天气、校务问答），一人一账号即可取全。
2. **登录是最大工程**：CAS 没有公开的移动端授权方式。可选路径按可行性排序：
   ① 企业微信/小程序渠道（学校已有）→ ② WebView 内嵌 CAS 并复用 cookie → ③ 逆向表单登录（验证码/滑块，不可持续）→ ④ 申请正式 OAuth 接入（最稳，需校方配合）。
3. **"办事"不要重做，只做导航层**：133 个 workflow 应用本质是同一个平台的实例，APP 只需做「按场景聚合 + 跳转」，不值得逐个原生实现。
4. **真正值得原生做的只有 5–8 个高频场景**：课表、成绩/考试、空教室、一卡通余额、待办审批、校历日程、报修、图书馆。
5. **一卡通不在门户里，在微信企业号里**（已查明，见 §3.7）：门户里只有「余额退款/销户」等办事流程，真正的余额/流水/充值在「北京中医药大学微信企业号 → e卡通」模块。原独立的校园卡网站 `ykt.bucm.edu.cn` **已失效**（http 连接失败 / https 404，指南页仍停留在 2023-03 未更新）→ APP 若要做一卡通，只能对接企业号侧接口或走圈存/现金的线下路径。
6. **合规是硬门槛**：抓取他人数据、长期维持登录态、上架应用商店都涉及授权与备案（见 `docs/05-可行性与合规.md`）。
